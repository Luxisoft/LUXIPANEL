# Static project deployment contract

Luxisoft/STORE introduced `surface: static` in source commit `5eb4cb34`.
The frontend `forms` and HTTP `forms-api` components are separate. Both preview
and production require this contract; an iframe alone cannot prepare a version.

The snapshot schema accepts `http`, `worker`, `mobile` and `static`. Existing
snapshots remain immutable and their canonical digest is checked. The tenant
runner builds an immutable image, exports `/srv/public` to a validated ZIP, and
does not start a web container for static components. The root supervisor stages
only the owned job's ZIP with validated size/hash and private permissions.

`GET /api/hosting/v1/accounts/:account/deployments/:project/jobs/:job/static/:component`
requires provider authentication, `deployments.read`, active account ownership,
a finished job, and matching SHA-256/size. It serves `application/zip` with
`private, no-store`. Maximum ZIP size is 32 MiB. `DELETE` on the same path requires
`deployments.write` and removes only staging bytes after the consumer has persisted
its verified artifact. It does not remove a release, source or user data.

Regression gates: `deployment-provider.service.test.ts` consumes the fixture
`__fixtures__/luxisoft-static-form.json`, generated by STORE's real deployment
analyzer from a synthetic Vite form + API project. Route tests cover permissions
and binary delivery. Run both before releasing the hosting API; keep the runner
and supervisor static export/staging support in installation packages as well.

Production verification must prepare a version through the consumer, verify the
ZIP digest, and open the generated preview with its API. An API health response
alone does not verify compatibility. Preserve local runtime wrappers and all
previous releases when installing a selective backend fix.
